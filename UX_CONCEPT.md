# GarageOS — UX-концепция v1.0

## 1. Главный объект системы

Основной объект в продукте должен быть не клиент и не автомобиль, а:

# Заявка на обслуживание

Пользователь думает в терминах реальной работы:

> «В 14:00 приедет Toyota Camry на замену масла»

А не:

> «Мне нужно создать Appointment, связанный с Vehicle, Client и Service»

Поэтому логика продукта строится так:

```text
КЛИЕНТ
   ↓
АВТОМОБИЛЬ
   ↓
ЗАЯВКА
   ↓
ЗАКАЗ-НАРЯД
   ↓
РАБОТЫ + ЗАПЧАСТИ
   ↓
ОПЛАТА
   ↓
ИСТОРИЯ
```

Важно: пользователь не должен сам создавать все уровни вручную. Система должна вести его по короткому сценариям.

---

## 2. Главная кнопка — «Новая заявка»

На каждом основном экране должна быть доступна основная CTA:

**＋ Новая заявка**

### На ПК

```text
┌──────────────────────────────────────────────────────┐
│ GarageOS                         🔍     ＋ Новая заявка │
└──────────────────────────────────────────────────────┘
```

### На телефоне

```text
┌───────────────────────┐
│ GarageOS          🔔  │
│                       │
│                       │
│                 ＋    │
│              Новая    │
│              заявка   │
└───────────────────────┘
```

На мобильном можно использовать плавающую кнопку, но основная функция должна быть именно "Новая заявка".

---

## 3. Создание заявки должно занимать 15–30 секунд

Формат: короткий, контекстный wizard, а не длинная форма на 30 полей.

### Шаг 1 — Клиент

```text
┌─────────────────────────────────────┐
│ Новая заявка                     ×  │
│                                     │
│ Клиент                               │
│ ┌─────────────────────────────────┐ │
│ │ 🔍 Имя или номер телефона       │ │
│ └─────────────────────────────────┘ │
│                                     │
│ Иванов Иван                         │
│ +7 777 123 45 67                   │
│                                     │
│ ─────────────────────────────────── │
│                                     │
│ + Создать нового клиента            │
│                                     │
│                  Далее →            │
└─────────────────────────────────────┘
```

Пользователь вводит номер или имя и системе сразу предлагается поисковый результат.

---

## 4. Если клиента нет — не выкидывать пользователя в список клиентов

Если клиента не существует, пользователь должен оставаться в той же сессии и просто создать клиента inline.

```text
Новый клиент

Имя
[ Иван ]

Фамилия
[ Иванов ]

Телефон
[ +7 777 123 45 67 ]

Комментарий
[ ]

[ Сохранить ]
```

После сохранения пользователь возвращается сразу в сценарий создания заявки.

## 10. Заявка и заказ-наряд — разные сущности

После создания заявки не нужно сразу создавать заказ-наряд. Это разные состояния процесса.

### Сценарий:

1. клиент записан;
2. автомобиль приезжает;
3. администратор нажимает "Принять автомобиль";
4. система предлагает создать заказ-наряд на основе заявки.

```text
ЗН-00152

Toyota Camry
Иван Иванов

Диагностика

Статус:
Автомобиль принят

Мастер:
Арман

Пробег:
125 400 км
```

Это уже рабочий документ.

## 14. Добавление работы должно быть быстрым

### Принцип

Не открывать длинную форму. Использовать быстрый inline picker.

```text
Добавить работу

🔍 Поиск услуги

Популярные:

Диагностика       15 000 ₸
Замена масла      10 000 ₸
Ходовая           20 000 ₸
Шиномонтаж        12 000 ₸

Цена
[ 15 000 ]

Количество
[ − 1 + ]

[ Добавить ]
```

Выбор услуги должен автоматически заполнять цену, но цену можно править вручную.

## 16. Функция «добавить всё одной строкой»

Администратор должен иметь возможность быстро вносить несколько позиций подряд.

```text
+ Добавить позицию

[ Замена масла          ] [10 000] [Работа]
[ Масло Motul            ] [25 000] [Деталь]
[ Фильтр                 ] [ 8 000] [Деталь]
```

Это важная скорость-операция для реальной работы в автосервисе.

---

## 17. Изменение заявки

Любой ключевой блок должен редактироваться прямо на месте.

```text
Дата
24 сентября, 14:00                 ✎

Мастер
Арман                              ✎

Автомобиль
Toyota Camry                       ✎
```

Нельзя заставлять пользователя ходить по нескольким страницам ради смены статуса или времени.

---

## 18. Мобильная версия — отдельный UX, не уменьшенная версия десктопа

### На телефоне нельзя делать длинную таблицу с 7 колонками.

Надо использовать компактные карточки:

```text
Toyota Camry
123 ABC 02

Иван Иванов
Сегодня • 14:00

🔧 Диагностика

🟡 Запланировано

[ Открыть ]
```

На мобильных устройствах продукт должен ощущаться как приложение, а не как адаптированная веб-страница.

## 22. Быстрые действия

На любом экране должна быть кнопка +, которая даёт контекстные действия:

```text
+

Новая заявка
Новый клиент
Новый автомобиль
Новый заказ-наряд
Добавить оплату
```

Если пользователь находится в карточке автомобиля, контент должен подстраиваться:

```text
Новая заявка для Toyota Camry

Новая запись
Новый заказ-наряд
Добавить работу
Добавить оплату
Добавить фото
```

## 23. Поиск должен понимать человека

```text
🔍 Поиск клиента, автомобиля или заявки
```

Примеры:

- `777123` → Иван Иванов;
- `123ABC` → Toyota Camry;
- `152` → заказ-наряд №152;
- `camry` → все машины Camry.

---

## 24. Автоматическое сохранение там, где это безопасно

Опции, которые можно сохранять мгновенно:

- статус;
- время;
- мастер;
- пробег;
- комментарии.

Но важные действия, которые могут разрушить данные, должны требовать подтверждения:

- удалить клиента;
- удалить автомобиль;
- отменить заказ-наряд.

## 28. Главный принцип UX

> Любое действие, которое администратор выполняет несколько раз в день, должно выполняться максимум за 2–3 действия.

### Примеры:

#### Добавить заявку

❌ 7 страниц

✅ Новая заявка → клиент → автомобиль → причина/время → Создать

#### Добавить работу

✅ + Работа → выбрать → Добавить

#### Принять автомобиль

✅ Принять → пробег → Создать заказ-наряд

#### Закрыть заказ

✅ Готов → оплата → Выдать автомобиль

## 29. Язык интерфейса

Интерфейс должен говорить языком бизнеса, а не языка базы данных.

### Не использовать

- CREATE
- UPDATE
- DELETE
- SUBMIT
- CANCEL

### Использовать

- Новая заявка
- Добавить работу
- Принять автомобиль
- Начать работу
- Готово
- Выдать автомобиль
- Добавить оплату

## 31. Главный вывод

> Не создавать сущности, а решать задачи.

Администратор СТО не должен думать про `Appointment`, `WorkOrder`, `Vehicle`, `Customer`.

Он должен думать так:

> «Приехал клиент. Нужно принять машину, назначить мастера, выполнить работу и получить деньги».

Именно такая логика должна лежать в основе UX GarageOS.

---

## 32. Практический приоритет для реализации

Для MVP следует сначала реализовать:

1. быстрый сценарий "Новая заявка";
2. карточка клиента и автомобиля в одном экране;
3. создание и изменение заявки inline;
4. создание заказа-наряда из заявки;
5. быстрый ввод работ и деталей;
6. статусная система "Запланировано → В работе → Готово → Выдано";
7. основной экран "Сегодня" как operational dashboard;
8. минимальный поиск по клиенту, автомобилю и заявке.

Это даст продукту ясную операционную модель и создаст сильное ощущение рабочего инструмента, а не обычной CRM-админки.
